SCREENS AND BEHAVIOR
1. Start Riding (01, 02): three picker cards (bike + setup, track, conditions). First ride: dashed prompts, CTA dimmed until all three filled. Returning: defaulted from the last ride, CTA live. Tapping a card opens its picker.
2. Track picker (03): search-or-name field at top; Recent list with per-track story line (rides count, saved baseline, usual setup); Nearby from the tracks table via the match_tracks RPC ("ridden by N others" from row counts); "New track here" creates a track pinned with one coarse location read (existing sanitizeLocation path). Free text always works offline.
3. Conditions (04): surface (hardpack, loam, sand, mud), track state (fresh, choppy, rutted), temperature band (cold under 50, mild, hot over 85), watered yes/no. Discipline-aware option sets are fine later; ship this set now. Rider-tapped only, nothing predicted.
4. Today's setup (05): the running setup for the chosen bike/setup, adjusted for conditions by the DETERMINISTIC client-side rule base (the Phase 1 decision; conditions_adjust_v1 engine mode stays later). Plain list, 32pt numbers, changed rows show old → new with a blue arrow, one sentence under the headline summarizing the tweaks. Tapping a changed row shows the reason. Applying these values creates no version yet; they become the day's starting deltas.
5. Ride mode (06): persistent session state on disk (started_at, bike, setup, track, conditions, current effective values, moto log, pending deltas). Elapsed time is the hero. Running numbers card. "Track changed? Retune" row opens 07. Huge Log moto, then Adjust and End ride. Survives app kill and reboot: resume on relaunch. iOS Live Activity (elapsed time plus a Log moto deep link) and Android foreground service with ongoing notification. "saved on phone" status reflects the local outbox; sync opportunistically; never block on connectivity; calm sync states only.
6. Mid-day retune (07): four tiles (just watered, roughed up, heating up, new track). New track routes back through the track picker. The others re-run the deterministic rule base against the current effective values and present old → new rows with a one-line reason. "Set it, back to riding" applies as pending deltas (still one settled version at end of day).
7. Log moto (08): Better/Same/Worse (56pt), then 4 large symptom chips plus "More symptoms" opening the full 14-chip taxonomy; terrain qualifier appears only for the ambiguous chips (harsh, rear kicks, packs) and is phrased per chip; optional on-device voice/text with the transcript shown and editable, feeding the existing free-text parse. Save writes a track_sessions row snapshotting effective values, sentiment, symptoms with qualifiers, and moto number.
8. Adjust (09): the engine's change set for the logged symptom plus qualifier, presented ONE change per screen with progress dots. Each shows old → new, the physical direction (clicks OUT/IN with rotation), and a reason; the next change's reason references the previous one. "Done, turned it" is the only thing that saves, and it records the new absolute value. "Different amount" opens a stepper for that adjuster only. "Skip" moves on. All suggestion content comes from the engine's rule base and helper functions; the UI must not hardcode symptom-to-adjuster mappings. Engine recommendation: cap at two changes per moto by default.
9. End ride (10): settles pending deltas into ONE manual version on the ridden setup's lineage (per the settle rule), adds elapsed time to bikes.hours, shows the moto timeline (sentiment per moto, change markers), stats (motos, editable ride time, engine hours), the dialed delta, and offers "Save as [track] baseline" (creates or updates that track's named setup), "Just save", and Share (a simple image card of the timeline and final numbers).
Forgotten sessions: if a session is open and the app is opened the next day (or after 12+ hours idle), prompt "Still riding?" with an editable end time; engine hours use the corrected time. No other prompts or notifications of any kind.

DATA (staged migrations, not pushed): ride_days (or reuse the plan's ride_day foundation) with the session fields above; track_sessions gains sentiment, symptoms [{id, qualifier}], moto_number, effective values snapshot; tracks + match_tracks per plan section 5; conditions stored on the ride day. Events: ride_day_started (with suggestion_shown/applied), moto_logged, adjust_shown, adjust_confirmed (with absolute value), retune_applied, ride_day_ended, baseline_saved, session_resumed, session_autoclosed.
