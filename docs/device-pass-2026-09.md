# Device pass, September 2026 (3.0 on dev-3-0)

Two scripted passes on a real device pointed at the preview branch `dev-3-0` (`.env.branch` swapped into `.env`; the branch is a prod clone, so use a test account, never a real rider's). Tick each box as you go and check the table or event named beside it right after the step, read-only, in the Supabase dashboard for project `rxbagshvbavrqtirprdz` or through `psql` on the session pooler. Every event lives in `public.usage_events` (`event_type`, `meta`, `created_at`); filter by your test user id. Every engine call lives in `public.tune_calls` (`mode`, `engine_source`, `input`, `output`).

Expected `engine_source` on dev-3-0 today: `app_config.baseline_engine` is `deterministic`, so a baseline (`mode = zero_baseline_v1`) answers `engine_source = deterministic` with `notes_source = llm` when the branch has an OpenAI key and `formula` when it does not; every refinement or conditions ask (`mode = tune2_v1`) answers `engine_source = deterministic`. `spend_limited` appears only if the OpenAI hard cap trips; `fallback_error` only if the model call itself throws. Anything else is a bug.

Before either pass: `npx expo start` with a dev client built after the tire and sag work (pure JS, the existing dev client is fine), airplane mode off, notifications allowed or denied (note which), and the test account's bikes noted (`select id, make, model, year, air_fork_override, tire_system_front, tire_system_rear from bikes where user_id = '<uid>'`).

## Pass A: an existing account on the Garage

Use an account that already has at least one bike with a baseline and is NOT Pro (so the refine gate can fire). Note the bike id as `<bike>`.

- [ ] A1. Open Garage. The list shows the bike with its dialed percentage and hours. Check: `bikes` row for `<bike>`; no event is expected.
- [ ] A2. Open the bike page. The meter card, Engine hrs and Tires tiles, the Setups list with the running setup badged, the Sag row, and (only if the bike sits on a 2016 SX, SX-F, FC or TC row with no answer yet) the air-or-coil banner. Check: `home_module_viewed` is NOT expected here (Home only); nothing to check yet.
- [ ] A3. Named setup (Pro door): tap New setup. As a free account the Pro gate sheet must appear naming "A second setup". Check: `usage_events` has `pro_gate_shown` with `paywall_trigger_action = second_setup`. Tap Not now.
- [ ] A4. Version history: tap the Setup story card. As a free account the Pro gate appears again (`pro_gate_shown` with `setup_history`). If the test account is Pro, the story opens and `story_opened` is logged; the versions listed match `select version_number, source, setup_id from setup_versions where bike_id = '<bike>' order by version_number`.
- [ ] A5. Rename (Pro accounts only): long-press a named setup row, rename it, save. Check: `bike_setups.name` changed for that `setup_id`; no event is expected.
- [ ] A6. Tire picker: tap the Tires tile. As a free account the gate fires with `tire_pressure`; on a Pro account the sheet opens. Set front 12, rear 12.5, front Tube, rear Mousse, Save. The rear stepper hides while Mousse is picked. Check: `bikes.tire_front_psi = 12`, `tire_rear_psi` null, `tire_system_front = tube`, `tire_system_rear = mousse`; the tile reads "12 / mousse". No event.
- [ ] A7. Sag recheck card first: open Home, tap Start riding, pick this bike. With no measurement on the bike the "Sag check" card shows under the pick cards. Check: `sag_recheck_shown` with `bike_id`, `last_measured_at` null. Tap Measure sag (this opens the page with `from = recheck`).
- [ ] A8. Sag page: read the why lines; enter A 610, B 577, C 506; the live numbers read static 33, riding 104; the riding verdict says in the window when the catalog window covers 104 (typical or factory range per the row); Save. Check: one `sag_measurements` row (`riding_mm = 104`, `static_mm = 33`, `version_id` = the running version, `bike_id = <bike>`); `setup_versions` UNCHANGED (versions are immutable); events `sag_measured_saved` (`riding_mm = 104`, `in_range`) and, because you came from the card, `sag_recheck_completed`. The History section lists the row. Back on the bike page the Sag row reads "104 mm riding".
- [ ] A9. Recheck card gone: Home, Start riding, pick the bike again. No Sag check card (last measurement is under `app_config.sag_recheck_ride_days`, 5 ride days). Check: no new `sag_recheck_shown`.
- [ ] A10. First free refinement: bike page, open the running setup sheet, tap Refine after ride. No gate (allowance 1). Log lands in quick mode: tap Log moto, pick a chip (Harsh on small bumps, tap once = mild), Save moto, then Adjust. Check after Adjust shows its change: `tune_calls` newest row `mode = tune2_v1`, `engine_source = deterministic`, `output.refine_allowance_remaining = 0`, `input.bike_id = <bike>`; events `moto_logged`, `adjust_shown`.
- [ ] A11. Confirm the change (Done, turned it) and Done. The sheet returns with the "That was your free refinement" line and a Go Pro button under the numbers. Check: `setup_versions` newest row for `<bike>` has `source = refinement`, `parent_version_id` = the version you refined from, `setup_id` matching that setup; `ride_feedback` has one row for the moto with `resulting_version_id` = that version (the feedback_link job); events `adjust_confirmed`, `version_created` (`source = refinement`), `free_refine_used` (`remaining = 0`).
- [ ] A12. Second refinement: tap Refine after ride again. The Pro gate sheet appears naming Refine after ride. Check: `pro_gate_shown` with `paywall_trigger_action = refine`. Tap the Pro row to open the paywall: `paywall_shown` with `paywall_trigger_action = refine` and `paywall_position = action_gated`. Back out: `paywall_dismissed`. Also confirm the server side: `select public.refine_allowance('<bike>')` as the test user returns 0.
- [ ] A13. 2016 banner (only if a test bike is a 2016 KTM 125/150 SX, 250/350/450 SX-F, Husqvarna FC 250/350/450 or TC 125, or add one through Add a bike and skip the quiz's fork question by answering it, then null `bikes.air_fork_override` by SQL to simulate a returning rider): the bike page shows "Your 2016 shipped with either air or coil forks depending on region. Which does yours have?" with two buttons. Tap Not now: banner hides; reopen the page: banner is back (nothing written). Tap Coil fork: banner gone. Check: `bikes.air_fork_override = false`; event `air_fork_override_set` with `source = banner`, `air_fork = false`. Open the setup sheet: the fork row is the spring row, not fork air.
- [ ] A14. Add a bike on a 2016 row from the Garage door: the quiz asks air or coil after the year, then the tire question. Check: `air_fork_override_set` with `source = quiz`; `bikes` row with `air_fork_override` and, if you chose, `tire_system_front / rear`.

Pass A tables in one query each: `bikes`, `bike_setups`, `setup_versions` (order by `version_number`), `ride_feedback`, `sag_measurements`, `usage_events` (order by `created_at`), `tune_calls` (order by `id`).

## Pass B: a full ride day

Same account, same bike. Start with airplane mode OFF.

- [ ] B1. Home, Start riding. Pick the bike and setup, pick a track (Recent, nearby via `match_tracks`, or Name this track: a new track stays on the device, that is known), pick conditions: surfaces hardpack then loam, state choppy, temp mild, watered yes. Tap Get today's setup. Check: `tune_calls` newest row `mode = tune2_v1`, `engine_source = deterministic`, `input.feedback.source = conditions`, `input.conditions.surfaces = [hardpack, loam]`, `input.tires` with the bike's systems and saved pressures, `output.tire_front_psi / tire_rear_psi / tire_reason / tire_source` present (`tire_source = conditions_adjusted` because watered), `output.refine_allowance_remaining` ABSENT (conditions asks are never counted). Today's setup shows at most two tweaks plus the Tires row (front 11.5 from the saved 12 with the half psi out, rear "mousse" if you left the mousse from A6).
- [ ] B2. Start the ride. Check: `ride_days` has one row (`bike_id`, `setup_id`, `track_id` or `track_name_raw`, `started_at`, `conditions`, `starting_version_id`, `local_id`); event `ride_day_started` (`suggestion_shown`, `suggestion_applied`). The clock runs on the mode screen.
- [ ] B3. Moto 1: Log moto, Harsh on small bumps tapped twice (bad), Save. Adjust: the engine proposes; confirm. Check: `tune_calls` row (`tune2_v1`, `deterministic`, `input.feedback.symptoms[0].severity = 8`, `input.conditions` present, `output.refine_allowance_remaining` PRESENT and 0 because the free refinement was used in Pass A; on a Pro account it is present too); `track_sessions` has one row for the moto (`duration_min`, `laps` if you entered them); `ride_feedback` has one row for the moto; events `moto_logged` (`moto = 1`, `sentiment`, `symptom_ids`, `qualifiers`), `adjust_shown`, `adjust_confirmed`.
- [ ] B4. Moto 2: log with Rear kicks plus the Jump face qualifier (tap once). Adjust and confirm. Check: a second `tune_calls` row with `input.feedback.symptoms[0].where = jump_face`; `track_sessions` and `ride_feedback` at two rows each; the events again with `moto = 2`.
- [ ] B5. Retune: tap Adjust for the day, tile Roughed up. On an MX bike the suggestion is fork compression one click OUT (softer); on an off-road bike, or after a moto logged bottoming, one click IN. Check: `tune_calls` row with `input.conditions.retune.tile = roughed`, `input.conditions.retune.discipline / skill / bottoming / state` filled, `engine_source = deterministic`; event `retune_applied` (`reason = roughed`, `source = engine` when online).
- [ ] B6. Moto 3: log with Better and no chip. Check: `moto_logged` with `moto = 3`, `symptom_ids = []`; no Adjust call is expected.
- [ ] B7. Airplane mode ON. Log moto 4 (Chatters, tap once). Adjust shows "Suggestions need signal. Adjust by hand, or try again when you have bars." Adjust by hand: fork rebound minus one, Done, turned it. Check on the device only: the mode screen shows the change; nothing reaches the server yet.
- [ ] B8. Still offline: log moto 5 (Same, no chip). Then End ride: enter hours if asked, Save. The toast reads "Saved on phone. Syncs when you have bars." Check on the device only: the End screen's summary lists 5 motos and the settled delta count; the session moved to history; the outbox holds jobs (`ride_day`, `moto` or `feedback`, `settle_version`, `feedback_link`; exact kinds per `lib/rideDay.ts`).
- [ ] B9. Airplane mode OFF. Open Home (or background and foreground the app). The outbox flushes. Check: event `sync_queue_flushed` with the job counts and zero failures. If it does not flush within a minute, reopen Home once more and note it.

Now the tables, in this order, all filtered to the test user and `<bike>`:

- [ ] B10. `ride_days`: still one row for today; `ended_at` set; `hours_added` if you entered hours; `ending_version_id` = the settled version (see B12); `conditions` is the morning's; `local_id` matches the device session.
- [ ] B11. `ride_feedback`: five rows, one per moto (motos 4 and 5 arrived with the flush), each with `symptoms` matching the chips (moto 1 severity 8, moto 2 `where = jump_face`, motos 3 and 5 empty), `overall_rating` from the sentiment, and `resulting_version_id` = the settled version on every row the `feedback_link` job reached.
- [ ] B12. `setup_versions`: exactly ONE new row from the ride day with `source = manual` (the End-ride settle: the settle rule is one manual version at End ride), `ride_day_id` = the B2 row, `parent_version_id` = the starting version, `notes[0]` "Ride day settled at ...: 5 motos, N changes", `sag_measured = false`, `setup_id` = the ridden setup. The Pass A quick refine is the only `source = refinement` row; no refinement row comes from a ride day. `version_number` continues the per-setup sequence.
- [ ] B13. `sag_measurements`: unchanged from Pass A (one row) unless you measured again.
- [ ] B14. `usage_events` for the day, in order: `ride_day_started`, `moto_logged` x5, `adjust_shown` x2 (motos 1 and 2; moto 4 was offline and by hand: `adjust_confirmed` with `custom = true` and no `adjust_shown`), `adjust_confirmed` x3, `retune_applied`, `ride_day_ended` (`motos = 5`, `settled_delta_count`), `sync_queue_flushed`, plus `qualified_trial` if this was the account's first ride day on a reverse trial, and `sag_recheck_shown` if the card was due at B1.
- [ ] B15. `tune_calls` for the day, in order: the conditions ask (B1), Adjust moto 1 (B3), Adjust moto 2 (B4), the retune ask (B5): four rows, all `mode = tune2_v1`, all `engine_source = deterministic`, `duration_ms` filled, `input.bike_id = <bike>`, `input.setup_id` = the ridden setup. No row for motos 3 to 5. Each row's `output` carries the four tire fields on the two conditions asks and none on the two symptom Adjusts (a symptom-only refine says nothing about tires).

Pass B done when B10 to B15 read as written. Anything that differs goes into the device-pass notes with the query that showed it.
